Slide 4: Why organize code?

Before we talk about modules and classes, let us first ask why organization matters.

When a program is very small, one file can feel simple. You might have a few variables, a loop, maybe a function, and a print statement. That is manageable.

But real analytics work often grows quickly. You may need to clean data, calculate metrics, create charts, run checks, and repeat parts of the process. If all of that logic is placed into one long script, the file becomes difficult to understand.

Organized code gives related work a clear home. For example, cleaning functions could go into a file called cleaning.py. Metric calculations could go into metrics.py. Chart functions could go into charts.py. Then a main file can use those tools without becoming too long.

This also helps future you. A few weeks later, when you return to the project, organized code makes it easier to remember where things are.

It also helps teams. If another person reads your work, clear file names, function names, and class names make the project easier to review.

The main idea is simple: organization reduces confusion. It helps code become easier to read, test, update, and reuse.

Slide 5: What is a module?

A module is a Python file that contains code you can use in another file or notebook.

Python already comes with many built-in modules. For example, the math module contains mathematical tools such as square root and pi. If we write import math, Python loads that module. Then we can use tools inside it, such as math.sqrt or math.pi.

A helpful analogy is to think of a module as a toolbox. The module is the toolbox, and the functions or values inside the module are the tools. When you import the toolbox, you can use the tools inside it.

One important detail is the dot notation. When we write math.sqrt, we are saying: go into the math module and use the sqrt function stored there.

This helps keep names organized. If every function from every module automatically appeared in our program without a module name, it would become difficult to know where things came from.

So a module helps with reuse, but it also helps with clarity. It tells us where a function or value belongs.

Slide 7: Aliases and selective imports

This slide introduces two common import patterns: aliases and selective imports.

An alias gives a module a shorter or more familiar name. For example, many Python programmers write import pandas as pd. That means we can type pd instead of pandas. The alias is helpful because it is short and widely recognized.

In this slide, we use import statistics as stats. This means the statistics module is available using the shorter name stats.

Selective imports work differently. When we write from datetime import date, we are importing only the date part from the datetime module. Then we can use date directly instead of writing datetime.date.

There is no single import style that is always best. If you need many tools from a module, importing the whole module can be clearer. If a short alias is common and recognizable, an alias can improve readability. If you only need one specific function or class, a selective import can be convenient.

The most important rule is this: use imports in a way that helps the reader understand where each tool comes from. Do not create confusing nicknames just to make the code shorter.

Slide 9: Create your own module

So far, we have used modules that already exist. Now we are going to think about creating our own module.

A module can simply be a Python file that you write yourself. For example, imagine a project with two files: main.py and calculations.py.

The calculations.py file can store reusable formulas, such as calculate_profit or profit_margin. The main.py file can run the analysis and use those formulas.

This structure keeps the main file shorter. Instead of placing every helper function directly into main.py, we move related helper functions into a separate file.

This is useful when a script starts to become too long. It is also useful when the same function is needed in more than one place.

A beginner-friendly way to think about this is: if you have a group of related helper functions, they may belong in their own module.

You do not need to build a large software project right away. The goal here is to understand the basic structure: one Python file can import useful code from another Python file.

Slide 11: What is a package?

A package is a folder that groups related modules together.

A module is usually one Python file. A package is a folder that contains related modules. For example, a project might have a folder called analytics_project. Inside that folder, we might have cleaning.py, metrics.py, charts.py, and main.py.

The package keeps related code organized. Instead of having many unrelated files scattered in one place, the package gives the project structure.

Large analytics tools are often packages or collections of packages. For example, libraries like NumPy and Pandas contain many modules and tools behind the scenes.

At this point in the course, you do not need to build a complex package. The main goal is to recognize the idea.

If a module is like one toolbox, a package is like a larger toolbox cabinet with several related toolboxes inside it.

Packages help keep projects from becoming one long file and make it easier to find related code.

Slide 12: Module, package, and library

This slide clarifies three related terms: module, package, and library.

A module is one Python file with reusable code. It might be a built-in module like math, or it might be a file you write yourself, such as calculations.py.

A package is a folder that groups related modules. For example, an analytics folder might contain cleaning.py, metrics.py, and charts.py.

A library is a larger reusable collection of tools. Libraries often include packages and modules. NumPy and Pandas are examples of libraries that many data analysts use.

These words are sometimes used casually, and people may not always use them perfectly. But the distinction is still helpful.

The simple rule is: module equals file, package equals folder, and library equals reusable collection of tools.

Understanding this vocabulary will help when you install and use Python tools later. When someone says to import a library, they usually mean to bring in a reusable toolset from a package or module.

Slide 14: What is a class?

Now we move into object-oriented programming.

A class is a blueprint for creating objects. The class describes what kind of data the object should store and what actions the object can perform.

For example, imagine a CustomerRecord class. Each customer record might store a customer ID and a segment. The class defines the structure, and each object created from that class stores its own values.

A useful way to think about this is that a class describes a general type of thing, while an object is one specific example of that thing.

For example, Product could be a class. One object might represent a laptop. Another object might represent a monitor. Both objects follow the same blueprint, but each one stores different values.

Classes are most useful when data and behavior belong together. If you only need one simple calculation, a function may be enough. But if you have a concept that stores information and also has actions related to that information, a class can be helpful.

Slide 16: One class can create many objects

One of the main benefits of a class is that the same class can create many objects.

Think about a Product class. The class can describe what every product should have, such as a name and a price. But each object can store different values.

One object might be a laptop with a price of 900. Another object might be a monitor with a price of 300.

Both objects come from the same class, but they are separate objects. Changing one object does not automatically change the other.

This is useful in analytics when we need to represent repeated things with the same structure. For example, customers, products, student scores, sales records, or reports could all be represented with classes in some projects.

The key idea is that a class gives us a reusable blueprint. Objects are the actual working examples created from that blueprint.

Slide 18: Methods and self

A method is a function that belongs to a class.

When a function is written inside a class, we usually call it a method. A method can use the data stored inside an object.

The word self is how a method refers to the current object. For example, if we have self.price and self.quantity, the method is using the price and quantity stored in the object that called the method.

This may feel strange at first, but the idea is practical. If we create several objects from the same class, each object has its own data. The method needs a way to know which object's data to use. That is the role of self.

In the Sale example, the total method multiplies self.price by self.quantity. The method does not need us to pass price and quantity again, because those values are already stored inside the object.

So the main idea is: attributes store data, methods define actions, and self connects a method to the specific object using it.

Slide 21: Function, dictionary, or class?

Beginners often wonder whether they should use a function, a dictionary, or a class.

A function is best when you need to perform one reusable task. For example, get_profit can receive sales and costs and return the profit.

A dictionary is best when you mainly need to store related values. For example, a product dictionary might store the product name and price.

A class is best when data and behavior belong together. For example, a Product class might store a price and also have a method that calculates the sale price.

The beginner rule is to start simple. Do not use a class just because it sounds advanced. If a function solves the problem clearly, use a function. If you only need to store related values, a dictionary may be enough.

Move to a class when one concept has both stored data and repeated actions.

This decision is part of writing clean code. The goal is not to use the most advanced tool. The goal is to use the right tool for the job.

Slide 22: Choosing the right organization tool

This slide summarizes the main organization tools from the module.

Use a function when you need one reusable task. For example, get_profit can calculate profit from sales and costs.

Use a module when you have a file of related functions or constants. For example, metrics.py might store several metric calculations.

Use a package when a project has several related modules that should be grouped together. For example, analytics_tools could be a folder containing cleaning, metrics, and reporting modules.

Use a class when data and behavior belong together. For example, SalesReport stores sales data and provides methods for total sales, average sales, and high sales count.

Use an object when you need one real instance created from a class. For example, report equals SalesReport creates one working report object.

The practical rule is to start with functions. Move to modules when the file becomes long. Use classes when one concept has both data and actions.

This decision-making skill is more important than memorizing syntax.

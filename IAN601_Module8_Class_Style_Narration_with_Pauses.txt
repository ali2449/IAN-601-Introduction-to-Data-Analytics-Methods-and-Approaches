Slide 1: Professional Practices

Welcome to Module 8, Professional Practices.

In this module, we are going to focus on habits that make Python code more professional. Up to now, we have mostly focused on learning how Python works. We have written variables, loops, functions, data structures, and small analytical examples.

Now we are going to ask a different question. What makes code easier to trust, share, maintain, and improve?

Professional code is not only code that runs one time. Professional code should be readable, reliable, tested, documented, reproducible, and respectful of data.

This matters in analytics because our code often supports decisions. If the code is confusing, fragile, undocumented, or careless with sensitive information, then the analysis becomes harder to trust.

As we move through this module, try to think like a future reader. That future reader might be your classmate, your coworker, your instructor, or even yourself two months later.

The goal is not to make the code look complicated. The goal is to make the code clear and dependable.


Slide 2: Learning path for Module 8

Here is the learning path for Module 8.

We will organize the module around four main areas.

First, we will talk about readability. This includes descriptive names, clear formatting, useful comments, and small pieces of code that are easier to understand.

Second, we will talk about reliability. Real data is often messy, so we need to know how to handle errors, validate inputs, and write code that fails safely.

Third, we will talk about documentation and testing. If we write a function that we want to reuse, we should explain what it does. We should also check that important behavior works as expected.

Finally, we will look at workflow practices. This includes Git concepts, reproducible project structure, and responsible handling of data.

These ideas may sound separate, but they are connected. Readable code is easier to test. Tested code is easier to trust. Documented code is easier to reuse. Reproducible projects are easier to share.

The main message is simple: professional code is written for future readers.

Slide 5: Exceptions help programs fail safely

Now let's talk about exceptions.

An exception is Python's way of saying that something went wrong while the program was running.

For example, Python may raise an error if we try to convert the text N A into a number, or if we try to divide by zero, or if a dictionary does not contain the key we expected.

In professional code, we do not want the entire workflow to fail just because one expected messy value appears in the data.

But we also do not want to hide every error.

This distinction is important.

Some problems are expected. For example, a dataset may contain missing values or invalid numeric entries. We can handle those safely.

Other problems are unexpected. For example, if our function has the wrong logic, we should fix it instead of hiding the error.

Good exception handling catches a specific error and responds in a clear way.

The pattern is: try to do something, catch the known problem, and return a safe result or message.

Slide 11: Git helps track changes

Professional work also requires a good workflow.

Git is a version control tool. It helps us track changes in a project over time.

Even if you are working alone, Git is useful because it creates a history of your project.

A typical workflow has a few steps.

First, you edit your working files.

Then you use git status to see what changed.

Next, you use git add to stage the files you want to include in the next checkpoint.

Then you use git commit with a message that explains the change.

Finally, if you are using a remote repository, you use git push to send your commits to that remote location.

A good commit message should describe the purpose of the change. For example, fix missing value handling is more useful than update file.

You do not need to become a Git expert immediately. But you should understand the basic idea: Git helps you save meaningful checkpoints as your project evolves.

Slide 14: Responsible data handling

Professional analytics is not only about code quality. It is also about responsible data handling.

Some data can identify people directly, such as names, email addresses, phone numbers, or IDs.

Other data can become identifying when combined with additional information.

A good practice is data minimization. Keep only the data needed for the task.

Another practice is masking. If we do not need to show the full value, we can hide part of it.

In the code example, the function mask_email keeps the first letter of the username and the domain, but hides the rest of the username.

This is only a simple demonstration. Real privacy requirements depend on the context, institution, and data type.

But the general habit is important: do not expose sensitive data unless there is a clear reason and permission to do so.


Slide 15: Reproducible project structure

A reproducible project is organized so another person can understand it and run it.

This does not mean the project must be complicated.

Even a small project benefits from clear structure.

A data folder can store input data or a small sample dataset.

A source folder can store reusable Python functions.

A notebooks folder can store exploration or teaching notebooks.

A README file explains the purpose of the project and how to run it.

A requirements file lists the packages needed to reproduce the environment.

This kind of organization reduces confusion.

It also helps you when you return to the project later.

If you have ever opened an old folder and wondered which file was the final version, then you already understand why reproducible structure matters.

Slide 18: Professional workflow checklist

Let's finish Module 8 with a practical checklist.

Before sharing or submitting an analytics project, ask yourself a few questions.

Is the code readable? Do the names and structure make sense?

Is the code reliable? Does it handle expected messy inputs safely?

Is the code tested? Do important functions have simple checks?

Is the code documented? Do reusable functions have docstrings, and does the project include basic instructions?

Is the project reproducible? Are files organized, and are dependencies listed?

Is the work responsible? Are sensitive data values minimized, masked, or protected?

You do not need to be perfect on every project. But these habits will make your work stronger over time.

The main takeaway is that professional analytics code should be clear enough to understand, safe enough to trust, and organized enough to reuse.
